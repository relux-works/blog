Однажды ночью наш оркестратор на Codex запустил дочерних агентов и стал
ждать, пока они закончат. Утром в логе было 173 автоматических продолжения за
48 минут: прочитать хвост лога, написать "без изменений", прочитать хвост лога
снова. Контекст за это время вырос со 120 до 470 тысяч токенов, и каждый из
466 вызовов модели переотправлял его целиком. Остановил цикл не человек и не
модель, а провайдер: в 00:03 он ответил 429 Too Many Requests.

Я стал смотреть, единичный ли это случай. На моём личном аккаунте Codex к тому
моменту было израсходовано больше 75 миллиардов токенов, и две трети из них за
последние три месяца. Это слишком много даже для очень плотной работы. Ниже
разбор того, куда они уходят, с цифрами из реальных сессий, с указанием на
конкретные места в исходниках Codex и со сравнением с тем, как та же задача
решена в Claude Code.

Текст написан простыми словами намеренно. Тут нет ничего, что нельзя объяснить
через две идеи: как считаются токены и что значит "подождать".

## Как считаются токены

Языковая модель не помнит разговор. Каждый раз, когда ей нужно сделать шаг,
ей заново отправляют всю переписку целиком, и она отвечает одним действием:
вызовом инструмента или текстом. Если переписка занимает 240 тысяч токенов, то
каждый шаг стоит 240 тысяч входных токенов. Неважно, что сам шаг это "выполни
`tail -n 18`". Плата идёт за то, что модель перечитывает, а не за то, что она
делает.

Формула стоимости любого ожидания получается простой:

```
стоимость ожидания = число шагов × размер контекста
```

Уменьшить можно либо число шагов, либо контекст. Дальше будет видно, что
goal-режим Codex ломает оба множителя.

### Короткий экскурс в KV-кэш

Чтобы обработать длинный контекст, модель считает для каждого токена набор
внутренних значений, их называют ключами и значениями, отсюда KV. Если
следующий запрос начинается с той же самой последовательности токенов, эти
значения можно не пересчитывать, а взять из кэша. Считать заново нужно только
хвост, который отличается.

В агентской сессии почти каждый запрос это предыдущий запрос плюс несколько
новых строк. Поэтому кэш попадает почти всегда. В проанализированном архиве
из кэша пришло 97.8% входных токенов.

Провайдеры отражают это в цене. У OpenAI кэшированный вход стоит 10% от
обычного, кэширование включается автоматически на промптах длиннее 1024
токенов, см. [документацию по prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).
При оплате по токенам через API это значит, что бесконечный опрос на большом
контексте дорог, но не катастрофичен: 90% объёма идёт по льготной цене.

### А что с подпиской

Подписка ChatGPT считает не деньги, а долю лимита в скользящем окне. Формула
расчёта этой доли публично не описана. Клиент Codex получает от сервера только
процент использования и время сброса, это видно в
[протоколе](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/protocol/src/protocol.rs)
в структуре `RateLimitWindow`. Учитывается ли там скидка за кэш, снаружи не
проверить. В той же документации по кэшированию OpenAI прямо говорит, что для
лимитов API кэшированные токены считаются как обычные. Единственное, что мы
знаем про подписку по опыту: сессии, где 98% входа было из кэша, всё равно
выбивали недельный лимит. Так что дальше я считаю входные токены целиком, без
скидки, потому что именно они, по всей видимости, определяют, когда вы
упрётесь в стену.

## Что значит "подождать"

Агент часто должен дождаться чего-то внешнего: сборки, тестов, другого агента.
Есть два способа это делать.

**Уведомление.** Агент делает один шаг "сообщи мне, когда закончится" и
отпускает ход. Пока ждём, шагов нет, значит нет и расходов. Когда событие
случилось, приходит одно сообщение, и это один новый шаг.

```
запустил → отпустил ход → тишина, ноль токенов → "готово" → один шаг
```

**Опрос.** Агент сам периодически проверяет: не закончилось ли? Каждая проверка
это шаг, каждый шаг это полный контекст.

```
проверил → 240k → "нет" → подождал → проверил → 240k → "нет" → ...
```

Опрос сам по себе не зло. Если между проверками можно поспать, не тратя шаг,
то он стоит столько же, сколько уведомление. Проблемы начинаются, когда
поспать нельзя.

### Если говорить языком async/await

Программистам проще думать про это как про задачу на планировщике. Ход
модели это запуск задачи, конец хода это точка, где задача отдаёт управление.
Дальше есть ровно три способа дождаться внешнего события, и они знакомы
любому, кто писал асинхронный код.

```
// 1. await: задача приостановлена, продолжение хранит планировщик
let result = await child.finished     // ноль вызовов, пока ждём
handle(result)                        // один вызов по событию

// 2. sleep-опрос: приостановка на фиксированный интервал
while !child.finished {
    await sleep(45s)                  // один вызов на каждый интервал
}

// 3. спин: задача не умеет приостанавливаться
while !child.finished {
    poll()                            // вызов за вызовом, без пауз
}
```

В обычном коде спин-ожидание просто греет одно ядро. У агента оно устроено
хуже: память модели это её контекст, и каждая итерация спина перечитывает всю
эту память заново. Это как цикл `while`, в котором на каждом обороте
копируется вся куча процесса.

[![Одна минута ожидания тремя способами: await, sleep-опрос, спин](/blog/codex-goal-token-burn/wait-primitives.png)](/blog/codex-goal-token-burn/wait-primitives.png)

Какой из трёх вариантов достаётся модели, решает не она. Это решает
диспетчер, который запускает её ходы, и набор инструментов, который ей
выдали. Дальше про то, что выдаёт Codex.

## Как ждёт Codex

У Codex есть нужный инструмент. Он называется `clock.sleep`: "поспи столько-то
миллисекунд, разбуди раньше, если что-то пришло". Реализация в
[`sleep.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/sleep.rs)
делает ровно это: засыпает до 12 часов и прерывается на новый ввод. Это
второй вариант из списка выше, и для ожидания он почти так же хорош, как
первый.

Только модель его не получает. Инструмент регистрируется по правилу из
[`spec_plan.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/spec_plan.rs):
он есть, если в каталоге модели указана поддержка `clock`, либо если его
включили в конфиге принудительно. Во встроенном
[каталоге моделей](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/models-manager/models.json)
`clock` есть у одной модели, `gpt-6-astra`. У `gpt-5.6-sol`, `gpt-5.5`,
`gpt-5.4` и у всех моделей с кастомных провайдеров список пуст. В `codex
features list` при этом написано `sleep_tool stable true`, но это флаг фичи,
а не факт наличия инструмента в запросе. В архиве из 3808 сессий `sleep`
вызывался 420 раз, и 418 из них сделала `gpt-6-astra`.

### Что остаётся без sleep

Единственный способ подождать это выполнить команду в шелле: `sleep 30`,
`tail` по логу, что угодно. Это шаг, а значит полный контекст. И у этого шага
есть потолок длины. Шелл в Codex работает через unified exec: команда
запускается в псевдотерминале, а инструмент отдаёт управление модели через
`yield_time_ms`. По умолчанию это 10 секунд, максимум 30, см. константы в
[`unified_exec/mod.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/unified_exec/mod.rs)
и умолчание в
[`handlers/unified_exec.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/unified_exec.rs).
Если процесс ещё жив, модель получает идентификатор сессии, и дальше может
дочитывать его вывод через `write_stdin` с пустым вводом. Такой пустой вызов
умеет ждать дольше, до пяти минут. То есть даже без `sleep` у модели есть
законный способ платить один вызов за пять минут ожидания.

В ночной сессии этот путь был закрыт. Модель работала через кастомного
провайдера и передавала числа в аргументах инструментов как дробные:
`60000.0` вместо `60000`. Парсер Codex ждёт целое и отвергает вызов. В архиве
это видно по всем сессиям на этой модели: 10 из 10 вызовов `write_stdin` и 23
из 25 вызовов с `yield_time_ms` упали с ошибкой вида `invalid type: floating
point 60000.0, expected u64`. Для такой модели потолок ожидания внутри одного
вызова это 10 секунд, и никакие флаги команды этого не меняют. Заодно это
значит, что принудительно включённый `sleep` ей тоже не поможет: его аргумент
`duration_ms` тоже целое.

## Что добавляет goal-режим

Без goal у модели есть запасной выход: закончить ход и замолчать. Даже без
`sleep` это даёт бесплатную паузу. Человек вернётся, напишет, тогда продолжим.
На языке планировщика это первый вариант, await: задача отдала управление, и
никто её не будит, пока не случится событие.

Goal-режим убирает и этот выход. Как только тред становится свободен,
goal-расширение немедленно отправляет модели новый ход "продолжай работать
над целью". Это видно в
[`extension.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/ext/goal/src/extension.rs):
обработчик `on_thread_idle` вызывает `continue_if_idle` из
[`runtime.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/ext/goal/src/runtime.rs),
а тот стартует ход сразу. Никакого бэкоффа, никакого счётчика пустых
продолжений. Бюджет токенов на цель по умолчанию не задан.

Слово "немедленно" здесь измеримо. В ночной сессии между концом одного хода и
началом следующего проходило от 0.02 до 0.05 секунды, медиана 0.03. Ход при
этом длился в среднем десять секунд: ровно столько, сколько нужно модели,
чтобы прочитать контекст, вызвать один опрос и написать "без изменений".
Частоту опроса задавала не модель, а её собственная задержка ответа.

[![Две с половиной минуты ночной сессии: ходы по 8–27 секунд с зазорами 0.03 секунды](/blog/codex-goal-token-burn/turn-cadence.png)](/blog/codex-goal-token-burn/turn-cadence.png)

На этой картинке есть момент, который объясняет всё остальное. В 23:50 человек
спросил модель, почему она так часто проверяет. Модель ответила честно и
точно: "Контракт гола требует каждый ход либо двигать работу, либо доказывать
verified wait живым опросом ранов", и пообещала опрашивать реже. Через 0.3
секунды после её ответа goal-режим запустил следующий ход. Обещание не могло
быть выполнено: модель не управляет тем, когда её вызовут в следующий раз.

Текст того самого контракта лежит в
[`continuation.md`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/ext/goal/templates/goals/continuation.md).
Там есть абзац про ожидание, и он важен. Ожидание засчитывается как настоящее
только если в этом ходу модель опросила живой процесс. "Я жду" без опроса
считается отсутствием прогресса. Модель сама может перевести цель только в
`complete` или `blocked`, причём `blocked` разрешён после трёх одинаковых
блокеров подряд, а ожидание детей блокером не считается. Поставить цель на
паузу может только человек.

Получается ловушка:

- закончить ход и подождать нельзя, тебя тут же перезапустят;
- перезапуск засчитается как "нет прогресса", если не опросить процесс;
- значит, каждый ход надо что-то опросить;
- каждый опрос стоит полный контекст.

Модель не глупит. Она делает ровно то, что от неё требуют. Просто требование
сформулировано так, что самое правильное поведение по контракту оказывается
самым дорогим по токенам. На языке планировщика goal-расширение это диспетчер
с одним правилом: очередь пуста, поставь ту же задачу снова. А контракт
запрещает задаче приостанавливаться иначе как через опрос. Вместе это спин,
третий вариант из списка.

## Как та же идея устроена в Claude Code

У Claude Code есть тот же режим, он тоже называется
[`/goal`](https://code.claude.com/docs/en/goal): задаёшь условие, и Claude
работает, пока оно не выполнено. Разница не в идее, а в диспетчере. Вот что
написано в документации, и что из этого следует.

| Событие | Codex, goal-расширение | Claude Code, `/goal` |
|---|---|---|
| Ход закончился, цель не достигнута | Новый ход через 0.03 с, решает сама модель через `update_goal` | Условие проверяет отдельная маленькая модель, и только тогда стартует новый ход |
| Ход закончился, но фоновая задача или сабагент ещё работают | Новый ход через 0.03 с, фоновые процессы не учитываются | Проверка пропускается, ход не стартует. Когда фоновая работа закончится, её результат приходит новым ходом |
| Фоновая работа тянется долго | Ничего, цикл продолжается | Первая проверка через 30 минут, дальше интервал удваивается, не больше трёх проверок без участия человека |
| Несколько ходов подряд без единого вызова инструмента | Ничего, цикл продолжается | Цикл останавливается с предупреждением, управление возвращается человеку |
| Лимит на цель | Бюджет токенов по умолчанию не задан | Счётчик ходов и токенов виден в статусе, ограничение задаётся в самом условии |

Ключевая строка там про фоновую работу: если сабагент или фоновая команда
ещё выполняются, проверка условия откладывается, а результат фоновой работы
доставляется модели как новый ход. Это и есть await из первого варианта:
задача отдала управление, диспетчер держит продолжение и будит её по
событию. Сами фоновые примитивы тоже есть: у Bash есть
[фоновый режим](https://code.claude.com/docs/en/interactive-mode#background-bash-commands)
с уведомлением по завершении, у сабагентов тоже, а
[Monitor](https://code.claude.com/docs/en/tools-reference) следит за потоком
событий и будит модель на каждой строке вывода. Документация по
[`/loop`](https://code.claude.com/docs/en/scheduled-tasks) прямо советует
использовать Monitor вместо опроса по таймеру, потому что это дешевле по
токенам.

Отсюда и ответ на вопрос, почему в сессиях Claude Code такого цикла не видно.
Не потому, что модель умнее, а потому, что диспетчер умеет ждать события и
умеет замедляться, когда ждать приходится долго. У Codex диспетчер умеет
только перезапускать.

## Пустые ходы

Есть и совсем тупой вариант той же ловушки. Модель заканчивает ход, ничего не
сделав, например, написала "жду". Goal тут же перезапускает её. Она снова
ничего не делает. Снова перезапуск. В логах есть цепочки по четыре таких хода
за 20 секунд. В одной сессии четырнадцать пустых ходов стоили 77 миллионов
входных токенов: ничего не произошло, а контекст был перечитан четырнадцать
раз. Именно от этого случая Claude Code защищается остановкой после
нескольких ходов без вызова инструментов.

## Почему это бьёт по оркестраторам

Наш оркестратор устроен так: он не пишет код сам, а раздаёт задачи дочерним
агентам, каждому в своей ветке и со своим контекстом. Так параллелится работа
и не раздувается контекст родителя. Но родитель должен дождаться детей, а их
обычно два или три.

Заблокироваться на одном ребёнке оркестратор умеет. Пока он ждёт первого,
второй может закончиться незамеченным. Поэтому модель боится долгой
блокировки и вместо этого бегает по логам всех детей по кругу. Каждый круг это
несколько шагов, каждый шаг это полный контекст. В сессиях ниже видно, что
оркестратор знал про блокирующее ожидание и использовал его, но между
блокировками всё равно опрашивал логи.

У Codex есть свой барьер по нескольким детям, инструмент `wait_agent` с
описанием "передай несколько идентификаторов, чтобы дождаться того, кто
закончит первым", см.
[`multi_agents_spec.rs`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/multi_agents_spec.rs).
Но он видит только агентов, которых сам Codex породил через `spawn_agent`.
Дети нашего оркестратора для него не существуют.

## Что было у модели той ночью

Сложим всё вместе. Вот способы подождать, которые теоретически есть у модели в
Codex, и что с каждым из них случилось в ночной сессии.

| Способ подождать | Что случилось |
|---|---|
| `clock.sleep` | Не выдан: у модели с кастомного провайдера нет `clock` в каталоге |
| `wait_agent`, барьер по нескольким детям | Дети не Codex-агенты, инструмент их не видит; в следующей сессии той же ночи попытка нативного `spawn_agent` вернула `unsupported call` |
| `write_stdin` с пустым вводом, до 5 минут за вызов | Единственная попытка упала: `floating point 36429.0, expected i32` |
| `yield_time_ms` длиннее 10 секунд | Единственная попытка упала: `floating point 60000.0, expected u64` |
| `sleep` в шелле | Десять раз по 4–8 секунд; всё, что длиннее 10 секунд, обрезал бы unified exec |
| Блокирующий флаг у команды наблюдения | Ни разу не использован, но он и не помог бы: тот же потолок 10 секунд |
| Закончить ход и подождать | Новый ход через 0.03 секунды |

Пять из семи дверей были закрыты средой, одну модель не нашла, и одна была
заперта контрактом. Осталось то, что мы видели в логе: один опрос на ход. Из 181
хода сессии 135 состояли ровно из одной такой команды.

[![Ночная сессия: 544 вызова модели, входные токены каждого вызова, goal-цикл выделен](/blog/codex-goal-token-burn/night-session-calls.png)](/blog/codex-goal-token-burn/night-session-calls.png)

Эта картинка заодно ставит эксперимент, который в живой сессии не поставишь
специально. Пока goal активен, оранжевые столбцы идут сплошной стеной, и
каждый выше предыдущего, потому что контекст растёт. В 00:03 провайдер
отвечает 429, ход падает с ошибкой, и цикл замирает на час, пока не вернётся
человек. В 01:34 человек возобновляет цель, и опрос начинается снова, каждые
12 секунд. В 01:35 он нажимает Ctrl-C, цель встаёт на паузу, и через восемь
минут говорит "продолжим без goal". Дальше пять вызовов, работа сделана,
сессия закончилась. Один и тот же контекст, одна и та же модель, одна и та же
задача. Единственная переменная это диспетчер.

## Что показали сессии

Я взял все роллауты Codex с двух машин за июль, август и сентябрь: 3808
файлов, каждый это один тред, включая дочерние. В них 59.2 миллиарда входных
токенов и 129 миллионов выходных, из кэша пришло 97.8%. Версии CLI от 0.144
до 0.154, модели в основном `gpt-5.6-sol`, плюс `terra`, `luna`, `gpt-5.5`,
`gpt-5.4`, `gpt-6-astra`, `gpt-5.3-codex-spark`, а также Qwen 3.6 и
muse-модели через кастомных провайдеров.

Goal-режим был включён в 52 сессиях из 3808, это полтора процента. Вот
сколько они весят.

[![52 goal-сессии занимают 49% входных токенов из 3808 сессий](/blog/codex-goal-token-burn/goal-share.png)](/blog/codex-goal-token-burn/goal-share.png)

Полтора процента сессий съели половину токенов: 29.2 миллиарда из 59.2. Семь
самых дорогих сессий архива, от 1.8 до 5.7 миллиарда каждая, все с
goal-режимом. Самая тяжёлая сессия без него весит 1.2 миллиарда. Без
принудительного продолжения модель заканчивала ход и ждала человека, а это
бесплатно.

Вот одна из goal-сессий по ходам. Синие ходы начал человек или сам
оркестратор, оранжевые запустил goal-режим.

[![Сессия A: входные токены на каждый ход, goal-продолжения выделены](/blog/codex-goal-token-burn/session-a-timeline.png)](/blog/codex-goal-token-burn/session-a-timeline.png)

Оранжевые столбцы это часы опроса логов. Самый высокий, 71 миллион токенов,
это один ход длиной три часа с 439 вызовами инструментов, в основном `tail`
по логам детей. Справа четыре почти невидимых оранжевых столбца это пустые
продолжения за 20 секунд.

А вот главная цифра. Сколько стоит один час ожидания при сопоставимом
контексте.

[![Стоимость часа ожидания: от 0.5 миллиона с уведомлением до 188 миллионов в goal-цикле без sleep](/blog/codex-goal-token-burn/waiting-cost-per-hour.png)](/blog/codex-goal-token-burn/waiting-cost-per-hour.png)

Сессия A ждала 7.8 часа и потратила на это 650 миллионов входных токенов,
271 шаг в час. Сессия B ждала 92 часа и потратила 1.85 миллиарда, 43 шага в
час, в ней модель делала `sleep 30` через шелл 61 раз. Ночная сессия за 48
минут goal-цикла сделала 466 вызовов, 590 в час, и потратила 149 миллионов.
Верхняя полоска это оценка для того же контекста с уведомлением: один-два
шага на событие.

Между ними лежит измеренный случай с `sleep`. В архиве есть две goal-сессии
на `gpt-6-astra`, единственной модели, которой инструмент выдан. Модель
пользовалась им, 60 и 129 раз, спала по 45 секунд за вызов. Час ожидания
стоил ей 10–15 миллионов входных токенов при 55–100 вызовах. Это в 6–18 раз
дешевле спина, и всё же в 20–30 раз дороже уведомления: goal-режим
по-прежнему перезапускал её после каждого хода, 600 и 443 раза за сессию, а
спала она недолго. Sleep снижает цену цикла, но не убирает сам цикл.

Ещё одна деталь из данных. Qwen 3.6 через локальный llama.cpp показал тот же
рисунок, 21 ход из 22 в goal-сессии были чистым опросом. Инструмент паузы
гейтится по каталогу модели, а не по провайдеру, и это не особенность одной
muse-модели.

## Что с этим делать

Со стороны Codex это несколько маленьких правок, и у всех есть готовый
образец в соседнем продукте.

- Регистрировать `clock.sleep`, когда у треда активный goal, независимо от
  каталога модели. Слабее, но тоже работает: сделать режим `always_on`
  умолчанием при включённых goals.
- Добавить выдержку между продолжениями, когда предыдущий goal-ход был ходом
  ожидания или пустым ходом. Claude Code делает это через 30 минут с
  удвоением интервала и потолком в три автопроверки, и останавливает цикл
  после нескольких ходов без инструментов. Сейчас `continue_if_idle` стартует
  ход сразу.
- Принимать `60000.0` там, где ожидается `60000`. Модели с кастомных
  провайдеров пишут числа так, и из-за этого у них не работает ни один
  инструмент ожидания.
- Одна строка в `continuation.md`: назвать `clock.sleep` и долгий
  `write_stdin` допустимыми формами verified wait, иначе даже модель с
  инструментом пойдёт опрашивать шелл.

Со своей стороны мы делаем пять вещей. Включаем `sleep` принудительно через
конфиг `[features] sleep_tool = { mode = "always_on" }` и чиним сериализацию
чисел на стороне прокси для кастомных моделей, без второго первое бесполезно.
Учим оркестратор ждать нескольких детей одним блокирующим вызовом, чтобы
блокировка перестала быть страшной. Для моделей, у которых работают целые
числа, документируем пустой `write_stdin` на пять минут как штатный способ
ждать. Доставляем уведомление о завершении ребёнка в очередь треда, а не
прямым стартом хода, потому что прямой старт в занятый тред отклоняется. И
ставим бюджет токенов на каждую цель, потому что по умолчанию его нет.

Формула из начала статьи не изменилась: число шагов, умноженное на контекст.
Всё, что перечислено выше, уменьшает первый множитель. Второй множитель,
контекст, который растёт часами без компакции, это отдельная история, и она
заслуживает своего поста.
